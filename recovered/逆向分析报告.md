# 摩尔卡丁车逆向分析与恢复记录

结论：APK 提供了实质性的重建基础，但本目录不是可运行游戏，也不是已适配 iOS 27 的 IPA。

## 本次实际完成

- 静态分析原始 IPA 和 APK，未执行游戏、未连接游戏服务器、未修改原包。
- 使用 ILSpyCmd 9.1.0.7988 对两端三份游戏托管程序集导出 C#。
- 使用 UnityPy 1.25.4 解析资源，并针对旧版网格补充 OBJ 导出器。
- 资源解析器从资源中识别 Unity 3.4.0f5。不能据此认为现代 Unity 可以直接打开原资源文件。
- 保存场景和资源对象的类型树、path_id、外部文件引用；保留自定义 MonoBehaviour 的原始序列化字节。

## 关键发现

APK 的 Assembly-CSharp 与 firstpass DLL 保留可反编译的方法体，未发现 ILSpy 的 /*Error: 注释；这不是编译通过或语义完全正确的证明。

IPA 中这两份 DLL 的反编译结果出现 5,743 处“方法体只有 ret”的错误，另有 void 空方法。符合旧版 iOS AOT 构建剥离托管方法体的情况。因此 iOS 导出的 .cs 主要作为类型/字段/接口参考，不能拿它直接重建游戏逻辑。Android 方法体是当前重建的主要来源。

两端主程序集有 609 个相同相对路径的 C# 文件，Android 特有 32 个、iOS 特有 44 个。相同文件名不代表实现一致；完整差异清单见 code_audit.json。iOS 特有输入、车辆模拟组件等逻辑可能还要从 Mach-O 的 AOT 机器码恢复。

IPA 主程序仅 ARMv7，最低 iOS 4.1，SDK iOS 5.1，cryptid=0。APK 原生库也仅见 armeabi-v7a。两者的旧原生引擎都不能直接作为 ARM64 iOS 引擎使用。

## 输出结构与用途

- apk/Assembly-*：可读的 Android 逻辑代码，是后续迁移主参考。
- ipa/Assembly-*：iOS 类型结构参考，含大量空壳，明确不可直接编译使用。
- 各端 ReferenceAssemblies/：原始 DLL，供分析引用；不是现代 Unity 的运行依赖。
- 各端 RecoveredAssets/：按原序列化文件分组的 PNG、OBJ、文本、音频和 objects.jsonl.gz。
- objects.jsonl.gz：逐行 JSON，保存 path_id、类型和可解析类型树；tree_error 表示该对象未完整解析。
- raw_scripts/*.bin：自定义脚本组件的原始数据，后续需结合 DLL 字段定义解析，尚未恢复为 Unity 可直接使用的组件。
- asset_manifest.json：首次导出记录，含通用网格/音频导出器失败。后续 legacy_export.json 记录针对旧格式的补充恢复结果，两份需要一起看。
- code_audit.json：代码数量、空方法报错、平台桥接文件和两端类型差异。

OBJ 保留局部坐标顶点、可用的 UV/法线和子网格分组；不包含骨骼、动画、材质绑定和场景变换。导出时检查索引范围和每个子网格三角形数量。动画、骨骼绑定等原序列化字段仍在类型树中，不代表已经重建完成。

Android 有 10 个网格没有解包后的顶点，未导出 OBJ，数据仍在类型树中。iOS 3,440 个网格已全部通过上述结构检查并导出。音频按文件头识别常见格式，其余保留 .audio.bin，未做播放验证。贴图已成功解码保存，但没有逐张视觉核验。

## 后续工作与阻碍

1. 选择单机计时赛作为首个运行目标，恢复启动、赛道加载、玩家输入、车辆物理和 AI 链路。
2. 用 Android 方法体匹配 iOS 类型结构，补齐平台差异。原服务器登录、排行榜、联机是否可用目前未知。
3. 根据 path_id、外部引用和自定义组件数据恢复场景、预制体、资源路径及脚本关联。当前 JSON/OBJ 导出并不等于恢复 Unity 工程。
4. 在有编辑器的环境迁移旧 Unity API、GUI、粒子、着色器和物理行为，替换旧原生插件。iOS 广告、统计、文本输入等桥接需要单独处理。
5. 在安装 Unity iOS 构建模块及 Xcode 的 Mac 上编译 ARM64，并在目标系统真机验证、签名。当前环境是 Windows，只有 .NET 8 运行时，没有 .NET SDK；本次未完成代码编译、Unity 导入或 iOS 构建。

因此，本次已经证明“代码和大量资源可恢复”，尚未证明“游戏可在新系统正常运行”。不应把这些文件当作完整源码工程或可安装升级包。
